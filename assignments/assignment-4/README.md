1. Deep document understanding outperforms fixed-size chunking because it improves retrieval fidelity and index design, albeit with extra preprocessing cost. Deep document understanding improves retrieval fidelity because the chunks are more complete in terms of meaning. If a query's embedding is most similar to a chunk's embedding, that chunk is more likely to contain all the pertinent information when using deep document understanding. In contrast, with naive chunking, the retrieved chunk is more likely to be missing part of the information due to arbitrary splitting. Deep document understanding improves index design because metadata about the embeddings can be gleaned from the document, which can then be used to add parameters to chunks aside from the embeddings themselves. This results in a more structured index instead of a flat collection of text chunks. Obviously, naive chunking is computationally easier since it just splits up the text into chunks arbitrarily, such as every x characters, without needing to analyze the structure or meaning of the document. Therefore, deep document understanding does come with a higher preprocessing cost.
2.  Template-based chunking (as the name suggests) relies on a template or predefined structure, such as tables or reports with headings, subheadings, and paragraphs, when splitting text into chunks. Therefore, it would fail for loosely structured corpora like chat logs. On the other hand, Embedding-driven semantic segmentation splits text into chunks based on changes in the similarity of embeddings throughout the corpus. This splitting strategy can fail for highly structured documents because it may split apart information that is grouped together structurally rather than semantically. 
3. Hybrid Retrieval improves recall because it combines lexical and vector based retrieval strategies to reduce the chance of missing relevant information. It uses lexical retrieval to match for exact keywords in the query, while vector based retrieval matches based on meaning of the query by considering the context formed by the words. Re-ranking improves precision because the retrieved chunks are further sorted based on their relevance to the query, and the most relevant chunks are returned. Lexical retrieval may fail if information in the query is worded differently in the corpus such as "cheap" and "affordable". Vector based retrieval may fail when exact wording matters, especially for proper nouns. For example, a query like "Animal Farm book" may retrieve information about books about animal farms rather than the book written by Orwell. Hybrid retrieval may fail when the query is unclear both lexically and semantically. For example, a query like "Animal Farm cost" is ambigous, since it could be referring to the cost of the book or an actual animal farm, so the system may struggle to determine the most relevant chunk.

A multi-stage pipeline is superior to a single-pass ANN search because its recall is much better, and with its re-ranking stage it can sort through the retrieved data to improve presicison as well. Essentially, you're starting with a wider net, so you are much less likely to miss any relevant information, as opposed to a single pass ANN search, which only retrieves the nearest neighbors based on embeddings. The added re-ranking of retrieved information increases latency, but you end up getting more accurate results. However, a multi stage pipeline introduces the possibility of cascading error propogation, as misses on relevant information in earlier stages can lead to unnecesary and often illogical re-ranking of duds done in later stages. 
5. An Elastic-like hybrid store is favored by workloads that require both keyword and vector based retrieval, since it can support both lexical and semantic matching. A Vector-native DB is favored by workloads where vector based retrieval is the main priority, a workload where semantic similarity is much more important than just keyword matching. A Graph-augmented store is favored by workloads in which alot of the retrieval done has to do with relationships between pieces of data (like edges between nodes in a graph).
6. Query transformation is critical in RAG because the information in a user's query is most of the time not structured in the same way that it is in the corpus. Expansion and decomposition change the query so that it is easier to match to the correct information in the corpus. Static query to retrieval is just leaving the query as is, obviously this requires no further processing of the query so it is faster but can fail due to differences in the structure or phrasing of the query and the corpus. Iterative query refinement retries the query repeatedly, from different perspectives or phrasing, ultimately getting more relevant results and therefore improving recall. However, this additional processing increases latency.
7. A Dense Vector Space retrieves chunks based on vector similarity, meaning it matches based on semantic similarity between the query and the chunks. However, since the relationships between the chunks are not explicitly represented, compositional reasoning is limited. Retreival is also not very easy to explain aside from just saying the embedding vectors were similar. With a relational schema and knowledge graph, the relationships between chunks are explicitly represented so the compositional reasoning is stronger. Retrieval is also easier to explain as you can trace through the relationships between data to show how your query lead to a certain chunk. In particular, Knowledge graphs can be used for more complex relationships between data, which allows for even stronger compositional reasoning and retrieval explainability.

9. Vector memory is for storing past interactions as embeddings, allowing for new interactions to be compared semantically to old interactions. Retrieved information from past interactions can therefore be hard to explain (similarity is based on embedding vectors). Structured Memory stores information from past interactions in a structured way through explicit relationships, which makes information recalled to new interactions easy to explain. Episodic Logs store interactions with time as metadata, this can lead to higher precision in terms of relevance over time since the context of the conversation is maintained throughout each new interaction.
